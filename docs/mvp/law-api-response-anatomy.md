# 법령 API 응답 구조 해부 (주택법 예시)

> 국가법령정보센터 OpenAPI가 돌려주는 **법령 원형 JSON**을 실제 예시(주택법 시행예정본, 시행 2026-08-04) 하나로 블록별 해부한다. "각 구성요소가 무슨 내용을 담는가"를 값과 함께 본다. 의미·티어 매핑은 [[law-attributes|속성 카탈로그]], `eflaw`/`law`·제개정구분은 [[law-domain-basics|도메인 기초]] 참고. 우리 모델(`Law`)로의 변환은 [[Normalizer]]·[[component-specs]] §1.

## 0. 최상위 봉투

실제 응답 최상위는 `{"법령": { ... }}` 로 한 번 감싸여 온다. `LawEnvelope`가 이 `법령` 블록 유무로 정상/오류를 판별한다(오류도 HTTP 200으로 오므로 봉투 검사가 유일한 방어선). 아래는 그 **안쪽 `법령` 객체**다.

```
법령
├── 기본정보     ← 식별·메타·시간축
├── 조문         → 조문단위[]   ← 본문(그라운딩 핵심)
├── 부칙         → 부칙단위[]   ← 시행일·경과조치·적용례
├── 개정문                      ← 자구 단위 개정 지시문
└── 제개정이유                  ← 개정이유 및 주요내용(요약)
```

`eflaw`(시행예정=미래본)와 `law`(시행중=현재본)는 **완전히 같은 스키마**다 — `기본정보`의 상태·시행일자로만 갈린다(D42).

---

## 1. `기본정보` — 식별·메타·시간축

```json
"기본정보": {
  "법령ID": "001809",          // ★ 버전 불변 식별자 — 시행중↔시행예정 연결키
  "법령일련번호": "283191",     // MST — 버전마다 다름. 연결키로 쓰면 안 됨
  "법령명_한글": "주택법",
  "제개정구분": "일부개정",      // 이번 변경의 종류(제정/일부개정/전부개정/…)
  "법종구분": "법률",           // 법률/대통령령/총리령/부령/…
  "소관부처": { "content": "국토교통부", "소관부처코드": "1613000" },  // ⚠️ 중첩 객체 — 이름(content)만
  "공포일자": "20260203",
  "공포번호": "21323",          // ★ 이번 개정분 부칙을 거르는 필터 키
  "시행일자": "20260804"        // ★ 시행예정본은 미래일(오늘 이후)
}
```

- **`법령ID`가 연결키다.** 같은 법의 시행중본·시행예정본을 잇는 축. `법령일련번호`(MST)는 버전마다 바뀌므로 연결에 쓰면 안 된다.
- **`공포번호`는 부칙 필터 키.** 부칙은 이력 전체가 오므로(아래 §3) 이 번호로 "이번 개정분"만 골라낸다.
- **`시행일자`가 서비스의 핵심 시간축.** 시행예정본은 미래일이라 "곧 나에게 적용될 법"을 이 날짜로 잡는다. 같은 `법령ID`에 시행예정본이 여러 개일 수 있어 정본 단위는 `(법령ID, 시행일자)`다(D43).
- `소관부처`는 `{ "content": 부처명, "소관부처코드": 코드 }` 중첩이다. 통째로 평탄화하면 부처명과 코드가 줄바꿈으로 이어져 섞이므로 `content`(이름)만 쓴다.

## 2. `조문 > 조문단위[]` — 본문 (그라운딩 핵심)

각 원소가 한 조문. 실제로는 함정이 여럿 겹쳐 있다.

### (a) `조문여부` — 실조문 vs 편제 제목

```json
{ "조문번호": "1", "조문제목": "총칙", "조문내용": "제1장 총칙", "조문여부": "전문", "조문변경여부": "N" }
```
`조문여부`가 `"전문"`이면 **장·절 제목**(편제)이지 실조문이 아니다. `"조문"`인 것만 실조문으로 다룬다.

> ⚠️ **제목 행은 그 장 첫 조문과 같은 `조문번호`를 쓴다**(제1장 행 `"1"` · 제1조 `"1"`). 실측에서 한 버전 안에 번호가 겹치는 쌍이 12,528건, 시행예정본에서 `조문변경여부='Y'`인 제목 행이 274건이었다. 번호로 조문을 찾거나 변경 조문을 고를 때는 `조문여부="조문"` 행만 본다.

### (b) `조문내용`만 읽으면 본문이 빈다 — `항 → 호 → 목` 재귀 병합

```json
{
  "조문번호": "2", "조문제목": "정의",
  "조문내용": "제2조(정의) 이 법에서 사용하는 용어의 뜻은 다음과 같다.",   // 도입 문장뿐
  "항": [ { "호": [
    { "호내용": "1. \"주택\"이란 … 건축물을 말한다." },
    { "호내용": "2. \"준주택\"이란 … 대통령령으로 정하는 것을 말한다." }
  ] } ],
  "조문여부": "조문", "조문변경여부": "N", "조문시행일자": "20260804"
}
```
제2조의 실제 정의는 `조문내용`이 아니라 **`항 → 호 → 호내용` 중첩**에 있다. `조문내용`만 쓰면 본문이 비어 보인다 → [[Normalizer]]가 재귀 병합해 `Article.text`를 완성한다. **인용 근거가 여기서 나오므로** 병합 누락은 그라운딩 붕괴다.

위 예시는 줄인 것이다. **실제 응답의 항·호·목은 번호 필드와 내용 필드를 따로 준다**(주택법 제57조, 2026-11-01 실측):

```jsonc
"항": [
  { "항번호": "①",
    "항내용": "① 사업주체가 제54조에 따라 … 공급하여야 한다. <개정 2021.7.20, 2023.12.26>",  // 내용도 번호로 시작
    "호": [
      { "호번호": "1.", "호내용": "1. 공공택지" },
      { "호번호": "2.", "호내용": "2. 공공택지 외의 택지에서 … 지정하는 지역",
        "목": [ { "목번호": "가.", "목내용": "가. 삭제 <2023.12.26>" } ] }
    ] },
  // 현행본(target=law)에는 제개정 메타 필드와 가지호 번호가 더 붙는다
  { "항제개정유형": "개정", "항제개정일자문자열": "2020.8.18, 2021.4.13, …",
    "항번호": "②", "항내용": "② 제1항에도 불구하고 …",
    "호": [ { "호번호": "4.", "호가지번호": "2", "호내용": "4의2. 「도시 및 주거환경정비법」 …" } ] }
]
```

- **내용 필드는 항상 번호로 시작한다** — 시행예정본·현행본 원본 전수에서 예외 0(항 470·호 443·목 53). 번호 필드까지 이으면 번호가 두 번 들어간다.
- **번호·내용 없이 `호`만 담은 항**이 있다(정의 조문 등, 원본 1건에 10개). **`목내용`이 목록**으로도 온다(아래에 `1)`·`2)` 세부 항목이 붙을 때, 2개).
- 그래서 병합 규칙은 "줄 = 항·호·목의 **내용 필드** 하나, 번호·제개정 메타 필드는 넣지 않음"이다(D75). 이 줄 경계가 그대로 청킹의 분할 경계가 된다(§8).

### (c) `조문변경여부` 플래그 — diff·색인의 대상 선별기

```json
{ "조문번호": "18", "조문제목": "사업계획의 통합심의 등",
  "조문내용": "제18조(사업계획의 통합심의 등) 통합하여 검토할 수 있다.",
  "조문여부": "조문", "조문변경여부": "Y", "조문시행일자": "20260804" }
```
`"Y"`면 **이번 개정으로 바뀐 조문**. 주택법 실측은 조문단위 137개 중 `Y`가 **6개뿐** — 이 플래그가 [[DiffBuilder]] 대조 대상과 [[RAGIndexer]] 색인 대상을 직접 지목해 137→6으로 좁힌다(토큰·노이즈 절감).

> ⚠️ **`개정문` 정규식 파싱으로 변경 조문을 찾지 말 것** — 실측에서 인용된 타법 조문번호를 오탐하고 벌칙·과태료를 누락했다. **플래그가 정답**이고 `개정문`은 사람이 읽을 근거 텍스트로만.

### (d) 조문 이동 — `조문이동이전`

```json
{ "조문번호": "57", "조문제목": "이동된 조문",
  "조문내용": "제57조 …", "조문변경여부": "Y",
  "조문이동이전": "005600", "조문이동이후": "000000" }
```
`조문이동이전: "005600"` = 옛 제56조가 제57조로 이동. [[DiffBuilder]]가 이동을 신설·삭제와 구분해 표시한다.

- 값은 **6자리 = 조문번호 4자리 + 가지번호 2자리**다(`000703` = 제7조의3, `005600` = 제56조). [[Normalizer]]가 조문번호 형식(`7의3`, `56`)으로 바꿔 담는다.
- **이동이 없는 조문에도 `000000` 자리표시가 온다.** 0으로만 된 값은 '없음'이다 — 그대로 두면 변경 조문이 전부 이동으로 분류된다.

### (e) `조문가지번호` — 가지조

```json
{ "조문번호": "105", "조문가지번호": "2", "조문제목": "허가 유효기간 및 재허가", "조문여부": "조문", "조문변경여부": "Y" }
```
가지조(제105조의2)는 `조문번호`가 본조와 같은 `"105"`이고 가지 번호가 `조문가지번호`로 따로 온다. 가지가 없으면 빈 값 또는 `"0"`. 가지번호를 버리면 제105조·제105조의2·제105조의4가 번호·인용키·대조에서 전부 겹친다 → [[Normalizer]]가 `조문번호="105의2"`로 합친다.

## 3. `부칙 > 부칙단위[]` — 시행일·경과조치·적용례

```json
"부칙단위": [
  { "부칙공포번호": "13782", "부칙공포일자": "20160119",
    "부칙내용": "제1조(시행일) 이 법은 2016년 9월 1일부터 시행한다." },     // 옛 개정 — 버림
  { "부칙공포번호": "21323", "부칙공포일자": "20260203",                    // 이번 개정(=기본정보.공포번호)
    "부칙내용": "부칙\n제1조(시행일) 이 법은 공포 후 6개월이 경과한 날부터 시행한다. 다만, 제57조제2항제7호의 개정규정은 공포한 날부터 시행한다.\n제2조(통합심의에 관한 적용례) 제18조제1항의 개정규정은 … 최초로 사업계획승인을 신청하는 경우부터 적용한다." }
]
```

- **부칙은 이력 전체가 온다.** 위처럼 2016년 옛 부칙이 섞여 있어, 그대로 쓰면 옛 경과조치를 이번 개정으로 오인한다 → **`부칙공포번호 == 기본정보.공포번호`(21323)** 로 이번 개정분만 필터.
- **시행 규칙은 부칙 제1조에서 나온다.** "공포 후 6개월이 경과한 날" → `effectiveRule`, "다만 …" 단서가 있으면 **단계적 시행**(`enforcementType`). `ActionPlan`(기한)이 이 값에 의존한다.
- 제2조 같은 **적용례·경과조치**는 "누구에게 언제부터"를 정하는 핵심 근거다.

## 4. `개정문` — 자구 단위 개정 지시문

```json
"개정문": "주택법 일부를 다음과 같이 개정한다. 제18조제1항 각 호 외의 부분 중 … "
```
"어느 조문의 어느 자구를 어떻게 바꾼다"는 **법제처의 공식 개정 지시문**. 사람이 읽는 변경 근거로만 쓰고, 기계 파싱(정규식) 대상으로 삼지 않는다(§2c 경고).

## 5. `제개정이유` — 개정이유 및 주요내용 (요약)

```json
"제개정이유": "[일부개정]\n◇ 개정이유 및 주요내용\n주택건설사업 관련 심의를 효율화하여 … "
```
법령 전체를 사람 말로 요약한 블록. **[[RAGIndexer]]의 법령단위 요약 벡터 소스**(시나리오 B 모호질의→법령 검색)이자 `ImpactSummary`의 재료다.

## 6. 실측 함정 요약 (국가법령정보)

| # | 함정 | 대응 |
|---|---|---|
| 1 | `조문내용`만 읽으면 본문이 빔 | `항→호→목` 재귀 병합(Normalizer) |
| 2 | 부칙은 이력 전체가 옴 | `부칙공포번호 == 공포번호` 필터 |
| 3 | 변경 조문은 `조문변경여부='Y'` 플래그로 | 개정문 정규식 파싱 금지(오탐·누락) |
| 4 | `소관부처`가 중첩 객체(이름 + 부처 코드) | `content`(이름)만 사용 |
| 5 | `display=1` 이면 `조문`/`law`가 배열 아닌 **단일 객체** | 파서가 단일/배열 모두 처리 |
| 6 | 인증 실패도 **HTTP 200** + `{"result":"…검증에 실패…"}` | 봉투 검사(`LawEnvelope`) |
| 7 | 연결키는 **`법령ID`** (MST는 버전마다 다름) | 시행중↔시행예정 매칭은 법령ID |
| 8 | 가지조는 `조문번호`가 본조와 같고 `조문가지번호`가 따로 옴 | `105의2` 로 합침 |
| 9 | `조문이동이전/이후`가 6자리(번호 4 + 가지 2)이고 이동 없음도 `000000`으로 옴 | 0만 있으면 null, 6자리는 `7의3`·`56` 형식으로 |
| 10 | 장·절 제목 행이 그 장 첫 조문과 `조문번호`를 공유 | 번호 조회·변경 조문은 실조문(`조문여부="조문"`)만 |
| 11 | 항·호·목이 번호 필드(`항번호` "①")와 **이미 번호로 시작하는** 내용 필드(`항내용` "① …")를 따로 줌 | 내용 필드만 한 줄씩 잇는다 — 통째로 평탄화하면 번호만 있는 줄이 낌(D75) |
| 12 | 현행본 항에 `항제개정유형`·`항제개정일자문자열`, 호에 `호가지번호`가 붙어 옴 | 본문이 아닌 메타 — 넣지 않음. 가지호 번호는 `호내용`("4의2. …")에 있음(D75) |
| 13 | `목내용`이 문자열이 아니라 목록(세부 `1)`·`2)` 줄)으로 오기도 함 | 줄 단위로 펼침 |

## 7. 이 원형이 우리 모델로 가는 길

```
법령(JSON 원형)  →  RawLaw(출처 원형 DTO, Map 보유)  →  Normalizer(ACL)  →  Law/Article/Addendum
```

- 원형의 기벽(§6)은 전부 `RawLaw → Law` 변환(**Anti-Corruption Layer**)에 가둔다 — 하류는 깨끗한 `Law`만 본다([[component-specs]] §1.1).
- 재현: `python tools/probe_eflaw.py` (실 응답 확인). 픽스처: `core/src/main/resources/samples/housing-act.json`(축약), 실제 응답에서 조문 일부만 자른 `core/src/test/resources/samples/raw/housing-act-{pending-20270909,current-20270309}.json`.
- 원본 전체: `docs/mvp/raw-samples/`(§8).

### 8.2 원본 구조가 정한 것

| 원본에서 본 사실 | 청킹 결정 |
|---|---|
| 본문이 **조문 단위**로 구조화돼 오고, 조문 번호가 인용 키(`source_id`)·평가(Recall@K)의 단위다 | **1조문 = 1청크** |
| 조문 안의 자연 경계는 **항 → 호 → 목**이고, 내용 필드가 그 단위마다 한 덩어리다(§2b) | 긴 조문은 **줄(= 항·호·목 내용 하나) 경계**에서만 자르고, 이웃 청크와 직전 1줄을 겹친다. 줄 하나가 혼자 한도를 넘을 때만 글자 수로 자른다 |
| `조문변경여부='Y'`가 바뀐 조문을 직접 지목한다(§2c) | **바뀐 조문만** 색인. 바뀌지 않은 조문·시행중본은 색인하지 않음 |
| 편장절 제목 행이 섞여 있고 번호를 공유한다(§2a) | **실조문만** 청킹 |
| `제개정이유`가 법령 전체를 사람 말로 요약한다(§5) | 법령 단위 **요약 청크** 1개(같은 분할 규칙) |

### 8.3 실측 통계 (시행예정 863개 버전)

- **바뀐 조문 비율:** 실조문 83,084개 중 4,487개(**5.4%, 약 1/18.5**). 주택법 한 건의 137→6이 코퍼스 전체에서도 같은 규모다. 버전당 평균 5.2 · 중앙값 2 · p90 14 · 최대 58, 바뀐 조문이 0개인 버전 78개(요약 청크만 색인).
- **바뀐 조문 길이(글자, D75 수정 후 추정):** 중앙값 420 · p90 1,279 · p99 3,667 · 최대 8,107. **2,500자 초과 113개(2.5%)** — 97.5%는 분할 없이 1청크.
- **조문당 줄(항·호·목) 수(수정 후 추정):** 중앙값 6 · p90 18 · 최대 124 — 긴 조문도 줄 경계가 촘촘해 경계 분할이 가능하다.
- **개정 이유 길이:** 중앙값 370 · p90 1,397 · 최대 4,674(2,500자 초과 6개).
- **2,500자 기준:** 임베딩 모델(`text-embedding-3-small`) 입력 한도 8,191토큰, 한국어는 음절당 약 2~3토큰 → 최대 8,107자 조문은 분할 없이는 한도를 넘는다. 토크나이저 의존성 없이 보수적으로 잡은 안전선이다.

> "수정 후 추정" — D75 이전 저장본에서 번호만 있는 줄과 제개정 메타 줄을 뺀 값이다(DB엔 원본이 없어 전 코퍼스를 다시 정규화하지 않았다). 수정 전 저장본 기준은 중앙값 431 · p90 1,327 · 최대 8,469 · 초과 121개.

### 8.4 살펴보다 찾은 정제 문제 (D75로 수정)

- **증상:** 저장된 조문 본문에 번호가 두 번 들어갔다(`①` 줄 다음 `① 사업주체가 …`). 바뀐 조문 72,486줄 중 **33,875줄(46.7%)이 번호만 있는 줄**이었다(글자로는 3.4%). 현행본(기준선) 본문엔 `개정` 한 단어 줄·날짜 목록 줄·가지호 숫자 줄도 섞였다(전체 518,817줄 중 번호 줄 227,731 · 메타 줄 14,685).
- **원인:** 조문 병합이 공용 평탄화(`LawEnvelope.text`)로 항 아래 문자열을 **전부** 이어, 번호 필드와 제개정 메타 필드까지 본문 줄이 됐다.
- **청킹에 준 영향:** 글자 수로는 작아 2,500자 기준엔 거의 영향이 없었지만, "줄 = 항·호·목" 가정이 깨져 **직전 1줄 오버랩이 번호 한 글자만 겹치는** 경우가 많았다. 임베딩·LLM 입력엔 번호 토큰이 반복됐고, 현행 대비 화면에 메타 줄이 보였다.
- **수정(D75):** 내용 필드만 한 줄씩 잇고, 번호는 내용이 번호로 시작하지 않을 때만 앞에 붙인다. 바뀐 본문은 `revision`을 바꾸므로 다음 `run`이 다시 저장·색인한다(요약 재생성은 `summarize`, 유료).

### 8.5 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| 고정 길이 슬라이딩 윈도(예: 512토큰, 20% 겹침) | 조문 경계를 넘나들어 인용·평가 단위가 흐려진다. 97.5%의 조문은 애초에 자를 필요가 없다 |
| 법령 전문 임베딩(법령당 1벡터 또는 전 조문) | 바뀌지 않은 94.6%가 비용·검색 노이즈. 생성 근거는 정본 정확 조회라 전문 벡터의 실익이 작다 |
| 시행중 조문까지 색인 | "지금 법"과 "곧 바뀔 법"이 한 색인에 섞인다. 기준선은 diff용 정확 조회로 충분하다 |
| 토큰 수로 정밀 분할(jtokkit) | 초과 조문이 2.5%뿐이라 보수적 글자 수 기준으로 충분. 의존성을 늘리지 않는다 |
