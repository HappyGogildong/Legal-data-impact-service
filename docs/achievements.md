## 핵심 성과

### 1. 환각을 프롬프트가 아니라 코드로 막았다

- 모델에 넣는 조문마다 `source_id` 를 붙이고, 응답의 모든 주장이 **주입한 `source_id` 만 인용**했는지 검사한다. 실패하면 다시 생성하고, 끝까지 실패하면 답하지 않는다(fail-closed).
- 대상을 확정하지 못하면 분석하지 않는다 — 해소 4상태(RESOLVED · AMBIGUOUS · NOT_FOUND_YET · UNVERIFIED).
- 벡터 검색은 "어떤 법인지 찾기"에만 쓰고, 근거는 정본을 `(법령ID, 시행일)` 로 정확 조회해 넣는다. 유사도로 근거를 고르지 않는다(D55).

### 2. LLM 비용을 구조로 줄였다

- **사용자와 무관한 분석은 미리 한 번만** — 법령 요약·변경점(Layer A)은 배치가 만들고, 온라인은 저장본을 읽기만 한다. 온라인 Layer A 의 Opus 호출은 0(D80).
- **바뀐 조문만** 모델에 넣는다 — 137 → 6조문.
- **개인화(Layer B)만 실시간 호출**하고 사용자별 하루 한도, 익명 전체 하루 상한을 둔다(D69 · D81).
- **유료 호출 1회 = 1행** 기록(목적·모델·토큰·재시도·인용 검증 통과 여부)과 시점별 단가 표로 비용을 조회 시점에 계산한다. 비용 결정은 문서 한 곳에 설정값으로 모았다(D83, [[cost-policy]]).

### 3. 믿을 수 없는 외부 API 를 한 층에 가뒀다

국가법령정보 API 는 인증 실패도 HTTP 200, 결과 1건이면 배열 대신 객체, 기본값이 예고 없이 바뀌는 식으로 **예외 없이 조용히** 깨진다. 이런 형식 문제를 Anti-Corruption Layer(`LawEnvelope`·`LawConnector`)에서 흡수하고, 실측한 함정마다 테스트를 둔다. 아래 사례 C·D·E 가 이 층에서 고친 것이다.

### 4. 배치를 다시 돌려도 안전하게 만들었다

- 작업은 DB 큐, 워커는 `FOR UPDATE SKIP LOCKED`, 실행 전체는 advisory lock 으로 하나만.
- 내용 해시(revision)로 **바뀐 것만** 저장·색인 — 두 번 연속 실행해도 결과가 같고, 주간 `--full` 도 내용이 같으면 임베딩하지 않는다.
- 반복 실패는 격리(DEAD)하고 경보. 작업 소유권 토큰으로 중단된 실행의 늦은 완료가 결과를 덮지 못한다.
- 운영 첫 백필 1,754건이 실패 0으로 끝났다.

### 5. 저비용으로 직접 운영한다

- EC2 한 대 + docker compose, 매니지드는 DB(RDS)만. Terraform·ALB·ECS 없이 월 약 $55~60(추정).
- **SSH 포트를 열지 않는다** — 접속·포트 포워딩은 SSM, 비밀값은 Parameter Store 에서 실행할 때 환경변수로만 넘겨 디스크에 남기지 않는다.
- CI 가 arm64·amd64 이미지를 GHCR 에 올리고, **main 머지가 곧 배포**다(D86). GitHub 는 AWS 키 없이 OIDC 로 역할을 받아 전용 SSM 문서 하나만 실행할 수 있다(공개 레포라 역할이 털려도 "정해진 배포"만). 서버는 배치가 끝나길 기다리고, 잠금 뒤 이미 배포된 것보다 옛 커밋이면 건너뛴다. 롤백은 Actions 수동 실행에 이전 SHA.
- Grafana 대시보드 4종과 배치 경보 3개(격리 발생 · 26시간 완료 실행 없음 · 목록 미완주 연속)를 Discord 로 받는다.
- 구축에서 겪은 차이를 런북(20단계)과 [[ops-manual|운영 명령 매뉴얼]]에 되돌려 적었다.

### 6. 측정할 수 있게 먼저 만들었다

- 호출 기록(`llm_calls`)·질의 이벤트(`query_events`)·배치 실행 기록(`ingest_runs`)이 대시보드와 경보의 출처다.
- RAG 오프라인 평가 하네스와 정답 세트 39문항(운영 데이터 대조 검토), 회귀 게이트(기준선 대비 하락 시 실패)를 갖췄다. 첫 운영 기준선(2026-11-21, 39문항·시행예정 612법령): 주제만 말한 질문의 정답이 상위 3개에 든 비율 92.9%(13/14), 법령 이름을 댄 질문의 해소 57.1%(8/14), 관련 법령 없는 질문에 후보를 낸 비율 100%(5/5) — 약한 곳이 숫자로 드러났다. 보고서는 JSON·HTML 로 `docs/eval/reports/` 에 남는다.

## 대표 사례

형식은 문제 → 실측 근거 → 결정 → 결과. 전체는 [[troubleshooting/README|트러블슈팅]].

### 사례 A · 운영 첫 dry-run 의 경고 한 줄에서 "바뀐 법이 바뀐 조문 0"을 찾았다 ([[008-same-day-promulgations|008]], D85)

- **문제** 운영 첫 `run --dry-run` 이 성공하면서 "같은 (법령ID, 시행일) 중복 75건" 경고를 냈다. 버전 키 가정(D43)이 깨졌다는 신호였고, 코드는 첫 행만 쓰고 나머지를 버리고 있었다.
- **근거** EC2 에서 같은 목록을 받아 묶으니 48개 키 · 75행. 48개 모두 MST(공포본)가 달랐고 조문 본문은 **48/48 같았다**. 변경 표시는 44개 키에서 공포본 하나에만, 1개는 둘에 나뉘어 붙었다. 개정문·제개정이유는 48/48 달랐다. 변경 표시가 붙는 쪽은 공포일·공포번호·MST 어느 순서로도 고를 수 없었다.
- **영향** 첫 행이 표시 없는 공포본이면 **실제로 바뀐 법이 "바뀐 조문 없음"**이 되고, 다른 공포의 개정 이유·부칙이 빠진다.
- **결정** 하나를 고르지 않고 병합 — 본문은 하나, 변경 표시는 합집합, 개정문·이유는 공포 순으로 머리말을 붙여 잇고, 부칙 번호에 공포번호를 붙여 인용키 충돌을 막았다. 본문이 다르면 추측하지 않고 실패.
- **결과** 단위 11 · 통합 6건(RED → GREEN). 재배포 dry-run `mergedKeys=48`, 백필 뒤 병합 버전 48건 저장. 원천에 변경 표시가 아예 없는 3건은 한계로 남겼다.

### 사례 B · 테스트는 통과하는데 청킹이 무너져 있었다 ([[005-article-text-number-duplication|005]], D75)

- **문제** 조문 본문을 만들 때 항·호·목의 번호 필드까지 평탄화해, 번호가 두 번 들어갔다. "본문에 내용이 들어 있나"만 보는 테스트는 통과했다.
- **근거** 시행예정본의 바뀐 조문 72,486줄 중 **33,875줄(46.7%)이 번호만 있는 줄**. 글자 수로는 3.4%라 눈에 띄지 않았지만, 줄 단위로 자르고 겹치는 청킹의 경계·오버랩이 번호 줄에 낭비되고 있었다.
- **결정** 정규식으로 증상을 지우지 않고, 조문 전용 병합이 구조(항 → 호 → 목)를 따라 **내용 필드만** 잇도록 고쳤다. 정보 손실이 없는지 원본 전수 확인(내용이 자기 번호로 시작하지 않는 경우 0).

### 사례 C · 외부 API 의 기본값이 바뀌어 "정상 응답 0건"이 됐다 ([[007-eflaw-list-needs-nw|007]], D77)

- **문제** 시행예정 목록이 HTTP 200 · 오류 없음 · `totalCnt=0` 으로 왔다. 같은 요청이 석 달 전엔 899건을 줬다.
- **위험** 배치에서 0건 목록은 "끝까지 받았음"으로 판정된다 — 저장된 시행예정본 **전부를 "목록에서 사라짐"으로 보고 철회**할 수 있었다.
- **결정** 원하는 필터(`nw=2`)를 직접 보내고, 두 번째 방어선으로 판정 대상의 20%를 넘게 사라지면 그 실행은 사라짐 판정을 하지 않고 `PARTIAL` 로 남긴다.
- **교훈** 외부 API 의 기본값은 계약이 아니다. 0건이 정상 응답으로 오는 경로는 그 0건이 판정으로 이어지는지 본다.

### 사례 D · "현행본"이 미래본이었다 ([[006-current-law-by-promulgation-date|006]], D76)

- **문제** diff 기준선으로 받은 "현행" 법령이 시행일이 미래인 본문이었다. `target=law` 는 **공포일** 기준으로 현행을 고른다.
- **피해** 기준선과 시행예정본의 시행일이 같으면 같은 키라 시행예정 행이 시행중으로 덮이고, 그 버전은 영영 다시 받지 않는다. 로컬 DB 에서 오염 행 32건을 찾아 백업 후 정리했다.
- **결정** 시행일 기준 목록(`nw=3`)으로 현행을 고르고, 커넥터·적재·동기화 세 곳에 시행일 불변식을 두어 같은 일이 다시 생기면 저장 전에 실패시킨다.

### 사례 E · "환경 차이"로 보인 간헐 실패가 날짜에 달린 데이터였다 ([[004-jejeong-law-no-baseline-english-envelope|004]], D54)

- **문제** 같은 스모크 테스트가 어떤 날은 통과하고 어떤 날은 실패했다.
- **근거** 시행예정 938건의 응답 최상위 키를 전수 관측 — **제정 법령은 현행본이 없어** 영문 오류 봉투가 왔다. 첫 시행예정 법령이 제정인 날에만 실패한 것.
- **결정** 현행본 없음 = 제정(전부 신설)으로 도메인에 표현했다.

## 일하는 방식

- **spec-first** — 행위가 있는 클래스는 코드보다 컴포넌트 문서를 먼저 써서 계약을 못 박는다.
- **TDD** — 실패하는 테스트(RED)와 통과(GREEN)를 따로 커밋하고, 둘 다 빌드되게 한다.
- **결정은 기록으로** — 대안과 근거를 D번호로 남기고, 바뀌면 "개정됨"으로 잇는다(D01~D87).
- **측정 없는 최적화·수치 금지** — 병목은 지표로 확인한 뒤에 손대고(D48), 문서의 수치는 실측만 쓴다.
- **유료 호출은 옵트인** — 실제 모델을 부르는 테스트·평가는 명시적으로 켤 때만 돈다.
