# RAG 평가·회귀 프레임워크

**관련:** [[decision-log|D83]] · [[observability]] · [[cost-policy]] · [[analysis-prompt-spec|프롬프트 정의서]] §6 · [[embedding-benchmark|임베딩 벤치]]

> **이 문서는 목표 설계다.** 아직 구현되지 않은 부분이 많다. 지금 코드와의 차이는 §9, 구현 순서는 §10을 본다. v0.1의 `Recall@5 ≥ 0.80`, 자기검색 기준선, `tools/eval`(RAGAS)은 D83으로 폐기했다.

## 0. 목적

답이 틀렸을 때 **어느 단계의 책임인지** 가르고, 프롬프트·모델·검색 설정을 바꿀 때 **성능이 떨어지는지** 드러낸다. 운영에서는 실제 질문으로 품질과 비용을 계속 본다.

## 1. 평가 대상

LIA의 RAG는 일반적인 "검색한 조각으로 답하기"와 다르다. 벡터 검색은 **법령을 찾는 데만** 쓰고, 법령이 정해지면 정본을 정확 조회해 통째로 넣는다(D56). 모델은 근거의 `source_id`만 인용하고 원문을 쓰지 않는다.

```text
질문 → QueryPlanner(의도·법령·조문 추출, Haiku)
     → SourceAnalyzer(이름 해소) 또는 LawDiscovery(주제 검색)
     → Layer A: 저장본 읽기(요약·변경점, D80) / Layer B: ContextBuilder → Opus → 인용 검증
```

평가는 이 경로를 그대로 지나야 한다. 청크 검색만 따로 재면 서비스가 쓰지 않는 경로를 재게 된다.

## 2. 책임 영역과 지표

`기준선 후`는 실측 전에 숫자를 정하지 않는다는 뜻이다. 측정 방식은 **결정적**(코드·데이터로 판정), **정답 세트**(§5), **표본 판정**(§6.3, 사람이 판정) 셋이다.

### 2.1 Retrieval Quality

책임: `QueryPlanner`(추출) · `SourceAnalyzer` · `LawDiscovery` · `ContextBuilder`

| 항목 | 지표 | 정의 | 통과 기준 | 측정 |
|---|---|---|---|---|
| 법령 정확성 | 법령 해소 정확도 | 이름을 댄 질문에서 맞는 법령으로 해소한 비율 | 기준선 후 | 정답 세트 |
| | Hit@3, MRR | 주제만 말한 질문에서 정답 법령이 상위 3개에 든 비율, 정답 순위 역수의 평균 | 기준선 후 | 정답 세트 |
| 조문 정확성 | 지목 조문 일치율 | 질문이 지목한 조문을 맞게 추출·판정한 비율. 번호 추출이 Haiku라 100%를 전제하지 않는다 | 기준선 후 | 정답 세트 |
| 핵심 근거 검색률 | 필수 근거 포함률 | 변경 조문·개정문·부칙·기준선 대응 조문(옮겨진 조문은 옮기기 전 번호) 중 컨텍스트에 들어간 비율 | 100% | 결정적 |
| 불필요한 검색 | 무관 후보율 | 노출 후보 중 정답도 허용 법령도 아닌 비율 | 기준선 후 | 정답 세트 |
| | 미인용 근거 비율 | 주입했지만 답이 인용하지 않은 근거 비율. 품질이 아니라 비용 신호다 | 관측만 | 결정적 |

| 항목 | 지표 | 정의 | 통과 기준 | 측정 |

| 정보 완전성 | 변경 조문 인용 커버리지 | 변경 조문 중 주장이 인용한 비율. 값싼 대리 지표다 | 기준선 후 | 결정적 |
| | 핵심 변경 재현율 | 사람이 꼽은 핵심 변경 중 답에 담긴 비율 | 기준선 후 | 표본 판정 |

| | 답변 관련성 | Layer B 답이 그 질문에 답하는지 | 기준선 후 | 표본 판정 |

### 2.3 Reliability & Safety

책임: `QueryDispatcher` · `ArticleFocus` · `AnalysisEngine` · 배치의 버전 관리

| 항목 | 지표 | 정의 | 통과 기준 | 측정 |
|---|---|---|---|---|
| Abstention | 거부 재현율 (규칙 판정) | 없는 조문·안 바뀐 조문·저장본 없음을 맞게 거부한 비율 | 100% | 결정적 |
| | 거부 재현율·과잉 거부율 (LLM 판정) | 비법령·조작 법명 등에서 거부해야 할 질문을 거부한 비율, 답할 수 있는 질문을 거부한 비율 | 기준선 후 | 정답 세트 |
| | 무관 질문 후보율 | 관련 법이 없는 질문에 후보를 낸 비율 | 기준선 후 | 정답 세트 |
| Hallucination | 근거 밖 사실률 | 뒷받침되지 않는 주장 중 원문 어디에도 없는 의무·기한·금액을 만든 비율. 주장 지지율과 같은 판정에서 얻는다 | 치명 사례 0건 | 표본 판정 |
| | 숫자·날짜 대조 실패율 | 답의 숫자·날짜가 인용 원문에 없는 비율. 표기 차이로 오탐이 나므로 검토 신호로만 쓴다 | 관측만 | 결정적 |
| Confidence Calibration | 문턱값 구간별 정답률 | 동작을 가르는 점수(`SourceAnalyzer` 88·60, 검색 유사도 하한 0.3)의 구간별 정답률 | 기준선 후 | 정답 세트 |
| Temporal Accuracy | 시행예정본·기준선 선택 정확률 | 질문 시점에 맞는 버전과 시행 중인 기준선을 고른 비율(D43·D76) | 100% | 결정적 |
| | 낡은 저장본 노출 건수 | revision·프롬프트 버전·기준선이 어긋난 저장본을 내보낸 건수(D80) | 0건 | 결정적 |
| | 주장 속 시행일 일치율 | 답에 쓴 시행일·경과 규정이 원문과 일치하는 비율 | 기준선 후 | 표본 판정 |

### 2.4 Token & Cost

책임: 호출 구조와 설정([[cost-policy]]). 답변 품질과 별개라 영역을 나눈다. 토큰과 비용만 본다 — 응답 시간 같은 성능 지표는 Prometheus·Grafana에서 본다([[observability]]).

| 지표 | 정의 | 무엇을 결정하나 |
|---|---|---|
| 요청당 토큰·비용 | 호출 목적별 토큰 분포(중앙값, 상위 5%). 평균만 보면 긴 법령 몇 건에 가려진다 | 하루 한도, 모델 선택 |
| 일·월 누적 비용 | 호출 목적별 합계 | 예산 경보 |
| 재시도 낭비율 | 실패한 시도의 토큰 / 전체 토큰 | 프롬프트 개선, 재시도 횟수 |
| 출력 잘림률 | 종료 사유가 `max_tokens`인 호출 비율 | `max-tokens` 16000이 충분한지 |
| 조문당 입력 토큰 | 입력 토큰 / 근거 조문 수 | 긴 법령을 나눠 생성할지 |
| Layer A 실측 단가 | 요약·변경점 1건당 비용 | 약 $155 추정치를 실측으로 교체 |

## 3. 지표에서 뺀 것

| 항목 | 이유 | 대신 |
|---|---|---|
| 인용 정확성 | 주장에는 인용문 필드가 없고 `source_id`만 있어, 모델이 원문을 지어내거나 고칠 수 없다 | ID 실재는 런타임 불변식으로 보장한다(`FaithfulnessGate`, 단위 테스트). 올바른 조문을 골랐는지는 주장 지지율로 본다 |
| 주장별 `confidence` 보정 | 모델의 자기 신고값이고 판정·화면 어디에도 쓰이지 않아, 보정해도 달라지는 것이 없다 | 실제 동작을 가르는 문턱값을 검증한다. 화면이나 판정에 쓰게 되면 다시 넣는다 |
| Recall@k (법령 전체 변경 조문 기준) | 변경 조문이 30개면 Recall@5의 상한이 약 0.16이라 구조적으로 낮다 | 법령 단위 Hit@3, MRR |
| Precision@k | 질문당 정답이 하나면 Precision@3의 상한이 0.33이다 | 허용 법령을 함께 적은 무관 후보율 |
| LLM 판정자(RAGAS 등) | 게이트 판정자로 LLM을 쓰지 않는다(D14·D53). 판정자 자체의 검증도 필요하다 | 사람 판정. 표본이 늘어 감당이 안 되면 사람 판정과의 일치율을 재고 보조로 검토한다 |

`FaithfulnessGate`는 이름과 달리 인용의 **존재**만 본다. 통과해도 주장이 옳다는 뜻이 아니다.

## 4. 두 가지 평가

운영 로그에는 정답이 없다. 그래서 운영 배치가 오프라인 회귀를 대체하지 못한다.

| | 오프라인 회귀 | 운영 배치 |
|---|---|---|
| 묻는 것 | 바꿔도 나빠지지 않는가 | 실제 질문에서 어떤가 |
| 입력 | 정답 세트(레포에 버전 고정) | 운영 기록, 표본 |
| 시점 | 프롬프트·모델·검색 설정 변경 전, 수동 | cron |
| 재는 지표 | Hit@3, MRR, 해소 정확도, 조문 일치율, 무관 후보율, 의도 분류, LLM 거부, 문턱값 | 사유별 거부율, 재생성률, 후보 0건 비율, 인용 커버리지, 대조 실패율, §2.4 전부, 표본 판정 지표 |
| 비용 | 임베딩·Haiku 소액, `eval` 프로파일로 수동 실행 | 평가 자체는 호출 없음(판정자가 사람) |

운영 표본에서 찾은 실패는 정답 세트로 옮겨 다음 회귀에서 막는다(§7.5).

결정적 지표(필수 근거 포함률, 규칙 거부, 버전 선택, 낡은 저장본)는 일반 단위·통합 테스트로 CI에서 항상 돈다.

## 5. 오프라인 회귀

### 5.1 정답 세트

`core/src/main/resources/eval/` 에 둔다. 레포가 공개이므로 **실제 사용자 질문을 그대로 넣지 않는다.**

```json
{
  "query": "전세 사기 피해자 지원이 어떻게 바뀌어?",
  "kind": "ANSWERABLE",
  "expectedLawIds": ["..."],
  "acceptableLawIds": ["..."],
  "articleNo": null,
  "expectedDimension": "SUMMARY",
  "expectedReason": null
}
```

- **`kind`:** `ANSWERABLE`(답이 있음), `NO_MATCH`(관련 법령 없음), `REFUSE`(비법령·조작 법명 등).
- **`acceptableLawIds`:** 정답은 아니지만 후보로 나와도 잘못이 아닌 법령. 무관 후보율의 분모를 정직하게 만든다.
- **작성:** 실제 법령을 보고 초안을 쓰고 사람이 검토한다. 첫 세트는 약 30문항이다.
- **만료:** 시행일이 지난 법령은 시행예정 검색에서 빠진다. 평가 시점에 대상이 아닌 문항은 집계에서 빼고, 뺀 건수를 보고서에 적는다.

### 5.2 회귀 게이트

1. 한 번에 설정 하나만 바꾼다.
2. 같은 정답 세트로 돌려 보고서를 만든다.
3. 커밋된 기준선 파일과 비교해, 허용 오차보다 떨어지면 실패다.

- **기준선 조건:** 경쟁 법령이 적으면 점수가 부풀려지므로 **전체 색인 후** 잰다. 기준선에는 색인된 법령 수와 문항 수를 함께 적는다. 색인 규모가 크게 달라지면 다시 잰다.
- **허용 오차:** 30문항이면 한 문항이 약 3.3%p다. 오차를 한 문항보다 작게 두면 우연히 실패한다. 보고서에는 비율과 건수를 함께 적는다.
- **분모가 작은 지표:** 허용 오차가 `1/분모` 이상이라 분모가 1~2인 지표는 사실상 회귀를 잡지 못한다. 정답 세트에는 종류(거부, 관련 법령 없음, 조문 지목, 의도 차원)마다 문항을 충분히 둔다.
- **CI:** 유료 호출이 없는 가짜 데이터로 게이트 로직만 검증한다. 실제 측정은 수동이다.
- **실행:** `eval` 프로파일(`--spring.profiles.active=eval`)로 한 번 돌고 끝난다. 정답 세트 `lia.eval.gold`(기본 `eval/offline-gold.json`), 기준선 `lia.eval.baseline`(기본 `eval/offline-baseline.json`)은 클래스패스 또는 `file:` 경로다. 보고서는 표준 출력에 JSON 한 줄, 종료 코드는 0 통과 · 1 실행 실패 · 3 회귀. 계약: [[OfflineEvaluator]].

## 6. 운영 배치

### 6.1 구성

```text
core ──(응답 후 비동기 기록)──▶ 기록 테이블 ◀── ingest(호출 기록, 동기)
                                   │
cron ─▶ eval 컨테이너 ─────────────┘
           ├─ 만료 삭제 → 집계 → 판정 대상 추출
           └─▶ 평가 결과 테이블 ─▶ Grafana
```

- **eval 컨테이너:** `ingest`처럼 같은 이미지에 `eval` 프로파일을 두는 일회성 컨테이너다(`profiles`, `restart: "no"`, cron 실행). 상시 서비스가 아니다. 평가의 부하와 실패를 온라인 응답에서 떼어 놓되, 서버가 한 대라 자원은 완전히 격리되지 않으므로 메모리 상한을 두고 사용량이 적은 시간에 돌린다.
- **Layer A:** 같은 답을 여러 사용자가 받으므로 요청마다 평가하지 않는다. `law_summaries` 저장본을 버전당 한 번 평가하고, 요청 기록으로 어떤 답이 많이 나갔는지만 본다.

### 6.2 비동기 수집

- 응답 경로 밖에서 크기 제한이 있는 큐로 DB에 쓴다. 기록 실패가 사용자 응답을 막지 않는다.
- 큐가 차면 버리고 `lia.eval.log.dropped`로 센다. 버려진 건수가 많으면 비용·품질 집계를 믿지 않는다.
- 일회성 `ingest`는 종료 때 유실되지 않게 호출 기록을 동기로 쓴다.
- Kafka·Loki를 두지 않는다. 트래픽을 아직 모르고 서버도 한 대다. 컨테이너 로그는 `run --rm`과 함께 사라지므로 쓰지 않는다.

| 기록 | 내용 | 대상 | 보존 |
|---|---|---|---|
| 질의 이벤트 | 차원, 상태·거부 사유, 후보 수, 시도 횟수, 프롬프트 버전. **원문 없음** | 전체 요청 | 집계 후 정책 결정 |
| 평가 표본 | 마스킹한 질문, Layer B는 마스킹한 답, Layer A는 저장본 참조 | 표본만 | 30일 |
| LLM 호출 | §8 | 전체 호출 | 집계 후 정책 결정 |
| 판정 | 주장별 판정값. **원문 없음** | 판정한 표본 | 기준선 비교에 필요한 동안 |

### 6.3 표본 판정

eval 컨테이너가 판정 대상을 뽑으면 사람이 주장마다 **지지 / 부분 지지 / 미지지 / 근거 밖 사실**을 매긴다. 첫 구현은 파일로 내보내고 판정 결과를 다시 넣는 방식이다. 판정 화면은 만들지 않는다. 표본 수는 사람이 감당할 양을 먼저 재고 정한다.

## 7. 원문 보관 규칙

질문에는 개인 사정이 섞일 수 있다(D41·D73). 이 규칙은 표본 수집을 켜기 위한 조건이다.

1. **처리방침이 먼저다.** 처리방침 요약(S15)에 목적·항목·30일 보관·삭제를 싣기 전에는 표본 수집을 켜지 않는다. 설정 기본값은 꺼짐이다. 익명 사용자 고지 방식과 재동의 필요 여부는 법무 검토(#35)에서 정한다.
2. **마스킹 후 저장한다.** 주민등록번호·전화번호·이메일·긴 숫자열(계좌·카드)을 저장 전에 지운다. 원본은 어디에도 쓰지 않는다. 정규식이 놓치는 개인정보(이름, 사정 서술)는 남을 수 있으므로 "개인정보가 없다"고 말하지 않는다.
3. **식별자를 남기지 않는다.** `user_id`와 프로필 항목을 저장하지 않는다.
4. **삭제 약속을 지킨다.** Layer B 답에는 프로필 내용이 드러날 수 있고, 처리방침은 계정 삭제 시 함께 지운다고 약속한다. 그래서 로그인 사용자의 표본에는 삭제 키 `HMAC(user_id, 별도 비밀값)`를 둔다. 계정 삭제·프로필 동의 철회 때 이 키로 지운다. 익명 표본은 키가 없고 만료로만 지워진다. 삭제 키가 있으므로 가명 정보이며, 익명 정보로 취급하지 않는다.
5. **30일 뒤 지운다.** eval 컨테이너가 실행마다 만료 행을 지우고, 만료 행이 남아 있으면 경보를 낸다. cron이 멈춰도 드러나야 한다.
6. **접근을 좁힌다.** Grafana 계정은 집계 결과와 호출 기록만 읽고 표본 테이블은 읽지 못한다.
7. **밖으로 보내지 않는다.** 표본을 LLM 판정자나 외부 도구로 보내지 않는다. 판정 내보내기 파일은 레포 밖에 두고 판정이 끝나면 지운다.
8. **정답 세트에는 다시 쓴다.** 실패 사례를 정답 세트로 옮길 때 원문을 복사하지 않고, 개인 사정을 뺀 일반 질문으로 새로 쓴다.

감사 로그([[concurrency-and-reliability]] §4)와 다르다. 감사 로그는 근거 재현용으로 영구 보존하고 원문을 넣지 않으며, 평가 표본은 품질 측정용으로 30일만 둔다.

## 8. LLM 호출 기록

Prometheus만으로는 부족하다. 일회성 배치는 긁히지 않는데 가장 큰 지출이 `summarize`이고, 보존도 15일이다. 그래서 **호출마다 한 행을 DB에 남긴다.**

| 필드 | 설명 |
|---|---|
| 호출 목적 | 분류, 법령 발견 임베딩, 색인 임베딩, 요약, 변경점, 영향·대응, 대응 재생성 |
| 모델, 프롬프트 버전 | 비교의 축 |
| 묶음 키, 시도 번호 | 한 요청의 재시도를 묶는다. 재시도 낭비율의 근거 |
| 입력·출력·캐시 토큰 | thinking 토큰은 출력에 포함된다 |
| 종료 사유, 성공 여부 | 출력 잘림률의 근거 |
| 시각 | 서울 날짜로 집계 |

- **비용은 저장하지 않는다.** 토큰과 시점별 단가 표로 조회할 때 계산한다. 단가가 바뀌어도 기록을 고치지 않는다.
- **`user_id`와 내용을 남기지 않는다.**
- **대조:** 합계를 월 1회 Anthropic·OpenAI 청구액과 비교해 누락을 찾는다.
- **지금 상태:** `SpringAiReasoner`가 `.entity()`로 결과만 받아 사용량을 버린다. 번역기도 확인이 필요하다. 임베딩은 `PgVectorStore` 내부에서 호출되므로 토큰을 어떻게 얻을지 구현 때 확인한다.

## 9. 구현 상태 (`com.lia.core.eval`)

1단계에서 v0.1 평가 코드를 정리했다. 계약은 [[OfflineEvaluator]].

| 대상 | 상태 |
|---|---|
| `EvalCase`, `GoldenSet` | §5.1 형식. 실제 정답 세트(`eval/offline-gold.json`)는 3단계에서 쓴다 — 지금은 테스트용 합성 문항만 있다 |
| `OfflineEvaluator` | 질문을 `QueryPlanner` → `LawDiscovery`로 돌린다. 비슷한 이름의 법이 있는 경우는 해소 후보(거부 아님)로 센다 |
| `OfflineMetrics` | §2.1의 법령·조문 정확성, 무관 후보율, 관련 법령 없음 후보율, 거부 재현율·과잉 거부율, 의도 분류 |
| `RegressionGate`, `EvalReport` | 지표 방향과 한 문항 허용 오차로 기준선과 비교. 보고서 = 기준선 형식(JSON) |
| `OfflineEvalRunner`, `EvalConfig` | `eval` 프로파일 실행. 배포 래퍼 연결은 3단계 |
| `RagConfig` | 법령 발견 설정 3개만 |
| `FaithfulnessGate` | 유지. 런타임 불변식이지 품질 지표가 아니다 |
| 제거 | `Retriever`, `ChunkStoreRetriever`, `RagEvalRunner`, `SelfRetrievalGold`, `RefusalMetric`, `RagEvalLiveTest`, 옛 정답 파일 2개, Recall·nDCG |
| 후속 | 문턱값 구간별 정답률 — `SourceAnalyzer`가 점수를 밖으로 내주지 않는다 |

**결정적 지표를 맡는 테스트** — 평가 하네스가 아니라 각 컴포넌트 테스트가 CI에서 항상 확인한다.

| 지표 | 테스트 |
|---|---|
| 필수 근거 포함률 | `ContextBuilderTest` — 변경 조문·개정문·부칙·기준선 대응 조문, 옮겨진 조문은 옮기기 전 번호 |
| 규칙 거부 | `DiffHandlerArticleTest`(없는 조문·안 바뀐 조문), `LayerAHandlerTest`(저장본 없음) |
| 시행예정본·기준선 선택 | `SourceAnalyzerTest`·`QueryPlannerTest`(가장 이른 시행예정본, D43), `LawConnectorCurrentTest`(시행일 기준 현행, D76) |
| 낡은 저장본 노출 | `LawSummaryStoreIntegrationTest`(revision·프롬프트 버전·기준선), `GroundedSummariesTest`(인용이 지금 근거 밖) |
