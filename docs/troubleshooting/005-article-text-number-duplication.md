# 005 · 조문 본문에 항·호·목 번호가 두 번 — 청킹 줄 경계 붕괴

| | |
|---|---|
| 유형 | 파싱 · 정제 · RAG 청킹 |
| 발생 시점 | 2026-11-01 (청킹 전략의 근거 자료를 정리하다 발견) |
| 관련 | D75 · 커밋 `69bc31b`(정책) · `53d70d2`(실패 테스트) · `497c8aa`(수정) · `f1a18c7`(근거 문서) · `core/.../normalize/Normalizer.java` · [[law-api-response-anatomy]] §8 · `docs/mvp/raw-samples/` |

## 1. 문제 정의

청킹 전략(D55)의 근거를 남기려고 저장된 정본(`law_versions.payload`)을 열어 보니, 조문 본문(`Article.text`)에 **항·호·목 번호가 한 줄씩 따로 끼어** 있었다(주택법 제57조, 시행 2027-09-09).

```
제57조(주택의 분양가격 제한 등)
①
① 사업주체가 제54조에 따라 … 공급하여야 한다. <개정 2021.7.20, 2023.12.26>
1.
1. 공공택지
2.
2. 공공택지 외의 택지에서 …
가.
가. 삭제 <2023.12.26>
```

현행 대비(`diffVsCurrent`)의 "현행" 쪽에는 원본에서 보이지 않던 줄이 더 섞였다 — `개정` 한 단어 줄, `2020.8.18, 2021.4.13, …` 날짜 목록 줄, `4.` 다음 `2` 다음 `4의2. …`.

**왜 조용했나.**
- 내용이 빠진 게 아니라 **더해진** 것이라, 기존 테스트(`text().contains("\"주택\"이란")`처럼 포함만 검사)가 모두 통과했다.
- 늘어난 글자는 3.4%뿐이라 청킹의 2,500자 분할 기준에도 거의 영향이 없어 눈에 띄지 않았다.
- 하지만 청킹은 "**줄 = 항·호·목 하나**"로 보고 긴 조문을 줄 경계에서 자르며 **직전 1줄을 겹친다**([[RAGIndexer]]). 번호만 있는 줄이 끼면 그 가정이 깨지고, 겹침이 번호 한 글자(`③`)만 전달한다. 임베딩·LLM 입력에도 번호 토큰이 반복된다.

## 2. 가설

1. **API가 내용을 중복해서 준다** — 원본 응답 자체에 같은 텍스트가 두 번 있다.
2. **정제(Normalizer)의 병합이 번호 필드까지 잇는다** — 원본은 번호와 내용을 따로 주는데 병합이 둘 다 본문 줄로 만든다.
3. **기준선 쪽 잡음은 현행본 응답에만 있는 별도 필드 때문이다** — `target=law` 응답이 시행예정본(`eflaw`)과 필드 구성이 다르다.

## 3. 메트릭/실측 기반 원인 확인 (근거)

**원본 확인** — 같은 버전의 원본 응답을 받아 저장했다(`docs/mvp/raw-samples/eflaw-001809-20270909-raw.json.txt`, `law-001809-current-raw.json.txt`).

```jsonc
// eflaw(시행예정본) 제57조
{ "항번호": "①", "항내용": "① 사업주체가 …",
  "호": [ { "호번호": "1.", "호내용": "1. 공공택지" } ] }
// law(현행본) 제57조 — 메타 필드가 더 붙는다
{ "항제개정유형": "개정", "항제개정일자문자열": "2020.8.18, 2021.4.13, …",
  "항번호": "②", "항내용": "② 제1항에도 불구하고 …",
  "호": [ { "호번호": "4.", "호가지번호": "2", "호내용": "4의2. …" } ] }
```

- 가설 1 **기각** — API는 같은 텍스트를 두 번 주지 않는다. **번호 필드**와 **이미 번호로 시작하는 내용 필드**를 따로 줄 뿐이다.
- 가설 2 **확정** — `Normalizer.mergeArticleText`가 `LawEnvelope.text(article.get("항"))`를 불렀고, 이 공용 평탄화는 맵의 **모든 값**을 재귀로 이어 붙인다(`map.values().forEach(...)`). 번호 필드도 한 줄이 됐다.
- 가설 3 **확정** — 현행본 원본의 항·호 키를 집계하니 `항제개정유형` 33 · `항제개정일자문자열` 33 · `호가지번호` 35가 있었다. 시행예정본 원본엔 없다. 같은 평탄화가 이것까지 본문에 넣었다.
- **부수 발견** — 평탄화는 맵의 반복 순서를 그대로 따른다. 실제 JSON은 순서가 유지되는 맵으로 읽혀 드러나지 않았지만, 실패 테스트를 `Map.of`(순서 보장 없음)로 쓰자 줄 순서까지 뒤섞였다(`… / 4. / ② / 개정 / ② 다음 각 호의 …`).

**규모(SQL, 로컬 시행예정 863개 버전)**

| 대상 | 전체 줄 | 번호만 있는 줄 | 메타 줄(`개정`·날짜·숫자만) |
|---|---|---|---|
| 시행예정본의 바뀐 조문 | 72,486 | **33,875 (46.7%)** | 0 |
| 시행중본(기준선)의 실조문 | 518,817 | 227,731 | 14,685 |

- 바뀐 조문 글자 수 기준으로는 2,794,311자 중 93,882자(3.4%).
- 번호만 있는 줄 판정: `^([①-⑳]|[0-9]+(의[0-9]+)?\.|[가-하]\.)$`.

**고칠 때 정보가 사라지지 않는지** — 원본 두 건 전수에서 내용 필드가 자기 번호로 시작하지 않는 경우는 **0**이었다(항 470 · 호 443 · 목 53). 가지호는 `호번호` "4." + `호가지번호` "2" ↔ 내용 "4의2. …"로 맞았다. 예외 모양 두 가지도 확인했다 — 번호·내용 없이 `호`만 담은 항 10개, `목내용`이 문자열이 아니라 목록(`1)`·`2)` 세부 줄)인 경우 2개.

## 4. 해결 방안 비교

| 안 | 내용 | 평가 |
|---|---|---|
| A | 병합 결과에서 번호만 있는 줄·메타 줄을 **정규식으로 지운다** | 회피책 — 증상만 지운다. 날짜·`개정`·숫자 줄마다 규칙이 늘고, 실제 내용과 모양이 같은 줄을 지울 위험이 있다 |
| B | 공용 `LawEnvelope.text`가 번호·메타 키를 건너뛰게 고친다 | 부칙·개정문·제개정이유·소관부처 같은 다른 소비자까지 바뀐다. 조문 구조에 대한 지식이 범용 함수로 샌다 |
| **C** | **조문 본문 전용 병합** — 항 → 호 → 목을 구조대로 걸으며 **내용 필드만** 한 줄씩 잇는다. 번호는 내용이 그 번호로 시작하지 않을 때만 앞에 붙인다 | **채택.** 필드 의미에 기댄 정공법이고, 맵 순서에도 기대지 않는다. 번호를 조건부로 붙여 원본이 다른 모양으로 와도 정보를 잃지 않는다(Normalizer의 "드롭 금지" 원칙) |

**대가** — 본문이 바뀌면 `revision`(분석 영향 필드 해시)이 바뀐다. 다음 `run`이 모든 버전을 다시 저장·색인하고(임베딩 비용), 쉬운 요약 저장본은 낡은 것이 되어 `summarize`로 다시 만들어야 한다(유료 Opus, D67 ⓐ). 정확성이 우선이라 감수하고, 요약 일괄 생성은 클라우드 배포 뒤로 둔다.

## 5. 최종 적용·검증

**정책 먼저(D75)** — 결정 기록과 [[Normalizer]] 문서에 "줄 = 항·호·목의 내용 필드 하나, 번호·제개정 메타 필드는 본문이 아니다"를 적었다.

**실패 테스트(RED, 6개 실패 확인)**
- 번호 필드가 본문에 두 번 들어가지 않는다 / 현행본 제개정 메타 필드를 넣지 않는다 / 내용이 번호로 시작하지 않으면 번호를 앞에 붙인다 / 목록으로 온 목내용을 줄로 펼친다.
- **실제 응답 픽스처 2개**(원본에서 조문 일부만 잘라 냄, `core/src/test/resources/samples/raw/`)로 "번호만 있는 줄·`개정` 줄이 없다, 가지호 본문이 남는다"를 검사.
- 실패 메시지 예: `but was: <제57조(…) / 2020.8.18, 2026.9.8 / 2 / 4의2. … / 4. / ② / 개정 / ② 다음 각 호의 …>`

**수정(GREEN)** — `mergeArticleText`를 내용 필드 순회로 바꾸고, 단건이면 객체·여러 건이면 배열로 오는 블록을 목록으로 맞추는 `LawEnvelope.maps`를 더했다. 공용 `LawEnvelope.text`는 그대로 둔다.

**검증**
- 새 테스트 6개 통과. 백엔드 전체 684개 중 실패는 수정 전부터 있던 국가법령정보 라이브 스모크 6건(외부 빈 응답, CI는 건너뜀)뿐.
- before / after (제57조 ①항 첫머리):

```
before                          after
제57조(주택의 분양가격 제한 등)     제57조(주택의 분양가격 제한 등)
①                               ① 사업주체가 제54조에 따라 …
① 사업주체가 제54조에 따라 …       1. 공공택지
1.                              2. 공공택지 외의 택지에서 …
1. 공공택지                      가. 삭제 <2023.12.26>
```

- 청킹 입력 통계(수정 후 추정 — 수정 전 저장본에서 번호·메타 줄을 뺀 값, DB엔 원본이 없어 전 코퍼스를 다시 정규화하지 않음): 바뀐 조문 길이 중앙값 431 → 420자, 최대 8,469 → 8,107자, 2,500자 초과 121 → 113개(2.5%). 조문당 줄 수 중앙값 6 · p90 18.
- 로컬 재적재는 하지 않았다(로컬은 동작 확인만). 전체 재저장·재색인은 다음 정기 실행이, 요약 재생성은 클라우드 배포 뒤 `summarize`가 맡는다.

**교훈**
- **"내용을 포함하는가"만 보는 테스트는 더해진 잡음을 못 잡는다.** 본문처럼 하류(청킹·임베딩·화면)가 모양에 기대는 값은 **정확한 기대값**으로, 그리고 **실제 응답 모양**으로 고정해야 한다.
- **원본은 직접 열어 봐야 한다.** 해부 문서의 예시는 줄인 것이어서 번호 필드가 없었다. 청킹 정책의 근거를 데이터로 남기려다 정제 버그가 드러났다.
- **범용 평탄화는 구조를 모른다.** 필드의 의미가 중요한 곳(조문 본문)은 구조를 아는 전용 로직으로, 범용 함수는 의미가 상관없는 곳(부칙 원문·소관부처)에만 쓴다.

> **관련 미해결(범위 밖):** 같은 자료에서 현행본 API(`target=law`)가 시행일이 미래(2027-03-09)인 본을 돌려준 것을 함께 발견했다. diff 기준선의 정확성 문제라 별도로 다뤘다 — [[006-current-law-by-promulgation-date|006]] · D76.
