# 008 · 같은 시행일 공포본 여럿 — 첫 행만 쓰면 바뀐 조문이 0

| | |
|---|---|
| 유형 | API 통합 · 도메인 식별 키 |
| 발생 시점 | 2026-11-14 (운영 EC2 첫 `lia ingest run --dry-run`) |
| 관련 | D43 · D85 · 파일 `core/.../batch/Discoverer.java` · `core/.../normalize/PromulgationMerge.java` · [[IngestJob]] · [[Normalizer]] |

## 1. 문제 정의

운영 첫 dry-run 이 성공했지만 경고가 하나 붙었다.

```
[batch] 같은 (lawId, 시행일)이 목록에 중복 75건 — 식별 키 가정 확인 필요
[batch] 실행 2 SUCCESS — {listed=952, duplicateKeys=75, planned.SYNC=877}
```

버전 식별 키는 `(법령ID, 시행일)`이다(D43). `Discoverer` 는 같은 키가 또 오면 **첫 행만 쓰고 나머지를 버렸다**. 경고는 그 가정이 깨졌다는 신호였다. 로컬에서도 같은 목록을 받아 왔지만 경고를 눈여겨보지 않았다.

## 2. 가설

1. **같은 행 반복** — 페이지를 넘기는 사이 목록이 밀려 같은 MST 가 두 번 왔다. 무해
2. **MST 가 다른 행** — 같은 법령이 서로 다른 공포로 같은 날 시행된다(일부개정 + 다른 법의 부칙에 딸린 타법개정). 하나만 고르면 다른 공포의 내용이 빠질 수 있다

75건은 페이지 밀림으로 보기엔 많다 — 2를 의심했다.

## 3. 메트릭/실측 기반 원인 확인 (근거)

EC2 에서 배치와 같은 목록(`target=eflaw&nw=2&efYd=오늘~+10년`)을 받아 묶었다(2026-11-15).

| 항목 | 결과 |
|---|---|
| 중복 키 / 버려진 행 | 48 / 75 |
| MST 까지 같은 묶음 | **0** — 가설 1 기각 |
| MST 가 다른 묶음 | **48** |

묶음마다 공포본 본문을 받아 비교했다(48 묶음 전부).

| 항목 | 결과 |
|---|---|
| 조문 전체(번호·제목·본문)가 같음 | **48/48** |
| 변경 표시(`조문변경여부=Y`)가 정확히 한 공포본에만 | 44 |
| 두 공포본에 나뉨(상법 1개·5개) | 1 |
| 어느 공포본에도 없음 | 3 |
| 개정문이 다름 | **48/48** |
| 제개정이유가 다름 | **48/48** |

예: 평생교육법 `000851@2026-12-03` — MST 286437(타법개정, 공포 2026-06-02 제21720호)은 변경 6, MST 286439(일부개정, 같은 날 제21721호)는 변경 0. 본문은 같다.

변경 표시가 붙는 쪽에 규칙이 없다. 평생교육법은 공포번호가 작은 쪽, 제주특별법은 큰 쪽, 노동감독관 직무집행법은 공포일이 늦은 쪽(MST 는 작은 쪽)이다. 공포일·공포번호·MST 어느 순서로도 고를 수 없다.

**영향:** DIFF 는 `조문변경여부=Y` 조문만 현행본과 대조한다(D42). 첫 행이 표시 없는 공포본이면 **실제로 바뀐 법이 "바뀐 조문 없음"**이 되고, 요약·영향 분석의 근거에서도 그 조문이 빠진다. 어느 쪽을 골라도 다른 공포의 개정문·개정 이유·부칙이 빠진다.

## 4. 해결 방안 비교

| 안 | 내용 | 판단 |
|---|---|---|
| A. 변경 표시가 가장 많은 공포본 하나 | 수정이 작다 | ✗ 48건 모두에서 다른 공포의 개정 이유·부칙이 빠진다. 상법은 변경 조문 일부를 잃는다 |
| B. 식별 키를 MST 로 | 공포본마다 따로 저장 | ✗ 사용자에게는 한 시점의 한 법이다. 같은 본문이 두 번 색인되고 인용키(`LAW:{lawId}@{efYd}`)가 깨진다 |
| **C. 같은 키의 공포본을 하나로 병합** | 본문은 하나, 변경 표시는 합집합, 개정문·이유는 머리말 붙여 잇기, 부칙은 번호에 공포번호 | ✓ 채택(D85). 키·인용키는 그대로 |

## 5. 최종 적용·검증

- `Discoverer` — 같은 키의 MST 를 묶어 SYNC 하나로. 작업·정본의 `mst` 는 숫자 오름차순 쉼표 목록(`MstList`), 묶음이 달라지면(공포본 추가) 다시 SYNC. 경고 대신 `mergedKeys`(정보).
- `SyncHandler` — MST 마다 본문을 받고 `IngestService.store(목록, 목록)` → `Normalizer.normalizeAll` → `PromulgationMerge`.
- `PromulgationMerge` — 조문이 공포본끼리 다르면 영구 실패(추측해 고르지 않는다). 부칙 번호 `제21720호-제1조`(공포본마다 `제1조`가 있어 인용키가 겹친다).
- `LawConnector.fetchCurrent` — 같은 일이 시행된 뒤 현행 목록(`nw=3`)에도 생긴다. 현행 행이 여럿이어도 시행일이 같으면 모두 받아 병합한다(시행일이 다르면 여전히 예외).

**검증:**
- 단위 `NormalizerMergeTest` 11건 — RED(11건 실패) 확인 후 GREEN.
- 통합 `DiscovererIntegrationTest` 4건(묶음 SYNC·같은 묶음 건너뜀·공포본 추가 재SYNC·같은 행 반복) · `TaskHandlersIntegrationTest` 1건(MST 둘 → 본문 2회·병합 저장) · `LawConnectorCurrentTest` 1건(같은 시행일 현행 행 둘 → 본문 2회). RED(6건 실패) 확인 후 GREEN.
- core 전체 869건 — 실패 6건은 법령 API 라이브 스모크로, 로컬 IP 가 법제처 OPEN API 에 등록돼 있지 않다는 응답(`사용자 정보 검증에 실패`) 때문이다. 이번 변경과 무관하다.
- 운영 확인은 배포 후 dry-run 의 `mergedKeys`(48 예상)와 백필 뒤 병합된 버전의 변경 조문 수로 한다.

**남은 한계:** 어느 공포본에도 변경 표시가 없는 3건(국가재정법 2027-01-01 등)은 병합해도 바뀐 조문이 0이다. 원천 데이터 문제라 따로 본다.

**교훈:** "식별 키 가정 확인 필요" 같은 경고는 **버린 데이터의 모양**을 바로 확인한다. 같은 키로 보이는 행도 무엇이 같고 무엇이 다른지(본문·표시·부속 텍스트) 나눠 재야 고칠 방향이 나온다.
