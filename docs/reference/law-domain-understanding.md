> 법률 도메인이 처음인 사람을 위해 `Law`/`Article`/`Addendum` 필드가 각각 무엇을 뜻하는지 쉬운 예시로 푼 해설이다. 정밀한 계약·불변식은 [[Law]]·[[Article]]·[[Addendum]] 스펙, 용어 카탈로그는 [[law-domain-basics]]·[[law-attributes]] 참고.

좋아. 이 클래스는 **"법령의 시행 예정 버전 하나를 표현하는 도메인 객체"**라고 보면 된다.

법률 도메인 용어가 처음이면 `법령 → 조문 → 개정 → 부칙`의 관계부터 잡는 게 가장 쉽다.

## 1. 가장 먼저: 법령은 책 한 권이라고 생각하면 된다

예를 들어:

> 「개인정보 보호법」

이라는 **법령**이 있다고 하자.

그 법령 안에는 여러 **조문**이 있다.

```text
개인정보 보호법
│
├── 제1조 (목적)
├── 제2조 (정의)
├── 제3조 (개인정보 보호 원칙)
├── ...
├── 제30조 (개인정보 처리방침)
│
└── 부칙
    ├── 제1조 (시행일)
    ├── 제2조 (다른 법률의 개정)
    └── 제3조 (경과조치)
```

즉 가장 중요한 관계는:

```text
법령
 ├── 조문(제1조, 제2조, ...)
 └── 부칙
```

이다.

---

# 2. 법령(Law)이란?

네 클래스에서

```java
String title;
LawType lawType;
String ministry;
...
List<Article> articles;
List<Addendum> addenda;
```

가 표현하는 것이 **법령 자체**다.

여기서 법령은 반드시 "법률"만 의미하지 않는다.

예를 들어:

- 법률

- 대통령령

- 총리령

- 부령

- 조례

- 규칙


등을 포함하는 넓은 개념으로 사용할 수 있다.

그래서

```java
LawType lawType
```

가 있는 것이다.

예를 들어:

```text
title = "개인정보 보호법"
lawType = LAW
```

또는

```text
title = "개인정보 보호법 시행령"
lawType = PRESIDENTIAL_DECREE
```

같은 식이다.

---

# 3. 조문(Article)이란?

네 코드의

```java
List<Article> articles;
```

가 이것이다.

법령의 본문을 구성하는 각각의 규정이다.

예를 들어:

```text
제1조(목적)
이 법은 개인정보의 처리 및 보호에 관한 사항을 정함으로써...

제2조(정의)
이 법에서 사용하는 용어의 뜻은 다음과 같다.

제3조(개인정보 보호 원칙)
...
```

여기서 각각이 **조문**이다.

즉:

```text
Article
   ↓
제1조
제2조
제3조
...
```

그리고 조문 내부에는 다시 여러 단계가 있을 수 있다.

```text
제10조(수집 제한)

① 개인정보처리자는 개인정보를 수집할 수 있다.

② 개인정보처리자는 제1항에 따라 개인정보를 수집하는 경우...
```

이때

```text
제10조
 ├── ①
 └── ②
```

처럼 구성된다.

조문 하나를 단순화하면:

```java
class Article {
    String no;       // "10"
    String title;    // "수집 제한"
    String text;     // 조문 내용
}
```

정도로 생각하면 된다.

# 4. 부칙(Addendum)은 무엇인가?

여기가 처음 보면 상당히 헷갈린다.

**부칙은 법령의 본문 조문과 별개로, 그 법령이 언제부터 어떻게 적용되는지를 규정하는 부분**이다.

예를 들어 어떤 법률이 개정되었다고 하자.

본문:

```text
제10조(개인정보의 처리)
...
```

그런데 개정했다고 해서 무조건 공포하자마자 적용되는 것은 아니다.

그래서 뒤에:

```text
부칙

제1조(시행일)
이 법은 공포 후 6개월이 경과한 날부터 시행한다.

제2조(적용례)
제10조의 개정규정은 이 법 시행 이후...
```

같은 내용을 붙인다.

이게 **부칙**이다.

따라서 네 모델에서:

```java
List<Addendum> addenda;
```

는

> 이번 개정에 따라 붙은 부칙들을 저장한다.

라고 이해하면 된다.

---

# 5. 공포일과 시행일은 다르다

법령 시스템에서는 이것이 굉장히 중요하다.

예를 들어:

```text
2026년 9월 1일
법률 개정안 공포

2027년 3월 1일
개정 법률 시행
```

이라고 하자.

그러면:

```text
공포
 ↓
2026-09-01
 ↓
아직 시행되지 않음
 ↓
2027-03-01
 ↓
시행
```

이다.

따라서 네 코드의

```java
LocalDate promulgateDate;
LocalDate effectiveDate;
```

가 각각:

|필드|의미|
|---|---|
|`promulgateDate`|법령을 공포한 날짜|
|`effectiveDate`|실제 법령이 시행되는 날짜|

이다.

그리고 네가 작성한

```java
// ★ 시행예정본은 미래일
```

은 정확히 중요한 포인트다.

시행 예정 법령이라면:

```java
promulgateDate = 2026-09-01
effectiveDate = 2027-03-01
```

같은 형태가 된다.

---

# 6. `effectiveRule`은 왜 필요한가?

시행일이 항상 날짜 하나로 딱 정해지는 것은 아니다.

예를 들어 부칙에:

> 이 법은 공포 후 6개월이 경과한 날부터 시행한다.

라고 되어 있을 수 있다.

또는:

> 이 법은 2027년 1월 1일부터 시행한다.

라고 할 수도 있다.

또:

> 제○조는 공포한 날부터 시행하고, 나머지 규정은 공포 후 6개월이 경과한 날부터 시행한다.

처럼 복잡할 수도 있다.

그래서:

```java
LocalDate effectiveDate;
String effectiveRule;
```

둘을 같이 가지고 있는 것이다.

```text
effectiveDate
→ 계산된 시행일

effectiveRule
→ 원문에 적힌 시행 조건
```

즉:

```text
"공포 후 6개월이 경과한 날부터 시행한다."
```

라는 원문을 보존하는 것이다.

# 7. 개정문(amendText)은 무엇인가?

이것도 RAG 시스템을 만든다면 상당히 중요한 개념이다.

법령이 개정될 때 실제로는 이런 식의 **개정문**이 나온다.

예:

```text
제10조제1항 중 "5년"을 "7년"으로 한다.
```

이것은 완성된 법령 본문이 아니다.

**"기존 법령을 어떻게 수정할 것인가"를 적은 지시문**이다.

그래서 네 코드의:

```java
String amendText;
```

주석:

```java
// 개정문 — 자구 단위 개정 지시문
```

이 정확하다.

개념적으로:

```text
기존 법령

제10조
보존기간은 5년으로 한다.


개정문

제10조제1항 중 "5년"을 "7년"으로 한다.


개정 후 법령

제10조
보존기간은 7년으로 한다.
```

이다.

즉:

```text
amendText
   │
   │ 적용
   ▼
기존 Article
   │
   ▼
새로운 Article
```

이라고 생각하면 된다.

---

# 8. `amendReason`은 개정문과 다르다

둘을 헷갈리면 안 된다.

```java
String amendReason;
String amendText;
```

### 개정이유

> 개인정보 처리자의 책임을 강화하기 위하여 보존기간을 5년에서 7년으로 연장하려는 것임.

즉 **왜 바꾸는가?**

### 개정문

> 제10조제1항 중 "5년"을 "7년"으로 한다.

즉 **정확히 무엇을 어떻게 바꾸는가?**

따라서:

```text
amendReason
= Why?

amendText
= How exactly?
```

로 이해하면 된다.

---

# 9. `promulgateNo`는 무엇인가?

```java
String promulgateNo;
```

는 **공포번호**다.

예를 들어:

```text
법률 제12345호
```

같은 식이다.

그리고 네 주석:

```java
// 부칙 필터 키
```

가 중요한 이유는 **부칙이 여러 개 섞여 있을 수 있기 때문**이다.

법령 데이터 원문을 수집하다 보면 특정 개정에 해당하는 부칙만 골라야 하는 경우가 있다.

그래서:

```text
공포번호
    ↓
이번 개정
    ↓
해당 개정에 속하는 부칙
```

을 연결하는 키로 활용하는 것이다.

---

# 10. `status`는 법령의 현재 상태

예를 들어:

```text
CURRENT
UPCOMING
EXPIRED
```

같은 상태를 생각할 수 있다.

예를 들어 오늘이:

```text
2026-09-02
```

이고,

```text
effectiveDate = 2027-01-01
```

이면:

```text
시행예정
```

이다.

반면:

```text
effectiveDate = 2026-01-01
```

이면 이미 시행 중이다.

즉 네 클래스의 목적에서는 대략:

```text
             법령
               │
       ┌───────┴───────┐
       ↓               ↓
   시행중 버전       시행예정 버전
   2026-01-01        2027-01-01
```

처럼 관리할 수 있다.

# 11. `lawId`와 `mst`의 차이

네 주석을 보면 이미 상당히 좋은 설계를 하고 있다.

```java
String lawId, // 법령ID (버전 불변)
String mst,   // 법령일련번호 — 버전마다 다름
```

개념적으로:

```text
"개인정보 보호법"이라는 법령
        │
        ├── 2025년 버전
        │      mst = A
        │
        ├── 2026년 시행중 버전
        │      mst = B
        │
        └── 2027년 시행예정 버전
               mst = C
```

그런데:

```text
lawId = X
```

는 동일하게 유지될 수 있다.

따라서:

```text
lawId
→ 이 법령이 무엇인가?

mst
→ 이 특정 버전의 데이터가 무엇인가?
```

라고 이해하면 된다.

그래서 네 주석처럼 **시행중 ↔ 시행예정 연결에는 `lawId`를 사용하는 것이 적절**하다.

# 12. `baselineLawId`는 조금 더 특수하다

```java
String baselineLawId;
```

는 이름 그대로라면:

> 이 개정본이 어느 기준 법령을 바탕으로 하는가

를 표현하는 식으로 사용할 수 있다.

예를 들어:

```text
기준 법령
    │
    ↓ 개정
개정 법령
```

다만 이 필드의 정확한 의미는 **네 시스템에서 어떻게 정의했는지에 따라 달라진다.**

특히 `lawId`와 `baselineLawId`가 둘 다 버전 관계를 나타낸다면 의미가 겹칠 가능성이 있으므로, 이 부분은 별도로 명확한 불변식(invariant)을 정의하는 게 좋다.

---

# 13. `delegationClauses`는 무엇인가?

이것도 법령 시스템에서는 꽤 중요하다.

예를 들어 법률에:

> 개인정보의 보관기간 등에 필요한 사항은 대통령령으로 정한다.

라는 문장이 있다고 하자.

법률이 모든 세부사항을 직접 규정하지 않고:

```text
법률
 ↓
세부사항은 대통령령으로 정함
 ↓
대통령령
 ↓
구체적인 기준
```

처럼 **하위 법령에 세부사항을 위임**할 수 있다.

이런 문구가:

```java
List<String> delegationClauses;
```

에 들어가는 것이다.

예:

```text
"대통령령으로 정한다."
"총리령으로 정한다."
"환경부령으로 정하는 바에 따른다."
```

이런 것을 추출해 두면 나중에 법령 간 관계를 분석할 수 있다.

# 14. 전체 클래스를 다시 보면

이제 네 클래스가 상당히 명확해진다.

```text
Law
│
├── 식별
│   ├── lawId
│   └── mst
│
├── 기본 정보
│   ├── title
│   ├── lawType
│   ├── ministry
│   └── revision
│
├── 개정 정보
│   ├── amendKind
│   ├── amendReason
│   └── amendText
│
├── 시간
│   ├── promulgateDate
│   ├── effectiveDate
│   └── effectiveRule
│
├── 본문
│   └── articles
│
├── 부칙
│   └── addenda
│
├── 다른 법령과의 관계
│   ├── delegationClauses
│   └── baselineLawId
│
└── 수집/원본 정보
    ├── promulgateNo
    ├── sourceUrl
    └── lastSeen
```

특히 **시행예정 법령**이라는 관점에서는 다음 4개를 중심으로 이해하면 된다.

```text
                개정 법령
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
      조문         부칙       개정문
   Article      Addendum    AmendText
        │           │           │
        │           │           └─ 무엇을 어떻게 바꾸는가
        │           └───────────── 언제/어떻게 시행하는가
        └───────────────────────── 실제 법령 내용
```

### 가장 중요한 차이

|용어|쉽게 말하면|
|---|---|
|**법령**|법 자체|
|**조문**|법령 안의 `제1조`, `제2조` 같은 규정|
|**부칙**|시행일·적용례·경과조치 등을 정하는 뒤쪽 규정|
|**공포**|법령을 공식적으로 세상에 알리는 것|
|**공포일**|공식적으로 공포된 날짜|
|**시행**|실제로 법령의 효력이 적용되기 시작하는 것|
|**시행일**|실제 적용이 시작되는 날짜|
|**개정문**|기존 법령을 어떻게 고칠지 적은 지시문|
|**개정이유**|왜 고치는지 설명|
|**공포번호**|`법률 제○○○○호` 같은 번호|
|**법령ID**|같은 법령을 버전 간 연결하기 위한 식별자|
|**법령일련번호(mst)**|특정 버전의 법령 데이터를 식별하는 번호|

그리고 **RAG 관점에서는 `Article`, `Addendum`, `amendText`를 서로 다른 종류의 SourceBlock으로 취급하는 현재 방향이 꽤 합리적**이다. 특히 "현행 조문"과 "개정문"을 섞으면 검색 결과가 `"현재 법 내용"`인지 `"앞으로 변경될 내용"`인지 혼동될 수 있기 때문에, 지금처럼 도메인 단계에서 구분해 놓는 것이 중요하다.
