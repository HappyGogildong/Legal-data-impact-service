# 임베딩 벤치마크 계획 — OpenAI vs Upstage

**관련:** [[component-specs|컴포넌트 스펙]] §3.3 · [[v0.5-bill-discovery|아키텍처 v0.5]] §3.4 · [[decision-log|D32]]

임베딩 **벤더 1개를 데이터로 확정**하기 위한 벤치 항목·방법. 후보는 [[decision-log|D32]]에서 외부 API로 좁혔고, 여기서 **OpenAI vs Upstage** 둘을 비교한다. 데이터 수집 파이프라인이 코퍼스·정답셋을 공급한다(§6).

## 0. 후보

| 후보 | 모델 | dim | query/passage 모드 | 단가($/1M) |
|---|---|---|---|---|
| **OpenAI** | `text-embedding-3-small` | 1536 | 대칭(모드 없음) | ~0.02 |
| **Upstage** | `solar-embedding-1-large` (`-query`/`-passage`) | 4096 | 분리(한국어 특화) | 가격표 확인 |

> dim 4096(Upstage)은 1536 대비 저장·메모리 ~2.7× — 정확도 이득이 그 비용을 정당화하는지가 핵심 질문.

---

## 1. 평가 시나리오 (우리 두 용도 그대로)

**시나리오 A — 분석용 RAG (법안 조문 → 현행법 조문)**
- 쿼리: 법안의 *개정 조문* 텍스트
- 정답 문서: 대응하는 *현행법 조문*
- **정답쌍 자동 확보:** **신구조문대비표**가 현행↔개정 조문을 짝지어 주므로, 사람 라벨링 없이 대량 골드셋 생성 가능. ★

**시나리오 B — 탐색용 의미검색 (모호 질의 → 법안)**
- 쿼리: 모호한 자연어(주제·효과 묘사)
- 정답 문서: 해당 법안의 요약·LawFacts
- **정답쌍 확보:** ① 법안 제안이유/요약을 *paraphrase*해 질의 생성(준자동) + ② 사람이 작성한 모호 질의 소량(예: "사람들이 서로 경계하게 만드는 개인정보 법안") — 현실 분포 반영.

---

## 2. 지표

### 검색 정확도 (주 지표, 시나리오 A·B 각각)
| 지표 | 의미 |
|---|---|
| **Recall@k** (k=1,3,5,10) | 정답이 top-k에 포함되는 비율 |
| **MRR@10** | 정답 순위의 역수 평균(첫 정답이 위일수록↑) |
| **nDCG@10** | 순위 가중 정확도(정답 다수 시) |

### 운영 지표
| 지표 | 측정 |
|---|---|
| 단가 | $/1M 토큰 + **적재 1회 비용**(코퍼스 전량) + 월 쿼리 비용 추정 |
| 지연 | 쿼리 임베딩 1건 p50/p95 |
| 차원·저장 | dim → pgvector 인덱스 크기·메모리 |
| 처리량/한도 | 적재 시 배치 throughput, max input tokens(긴 조문), 레이트리밋 |
| 통합 | SDK·pgvector 연동 안정성 |

### 정성 (한국어·법률 도메인)
- 법률 조문체·전문용어 처리, 모호 질의(동의어·완곡표현) 강건성 — 실패 사례 정리

---

## 3. 방법론 (통제 변인)

1. **동일 코퍼스·동일 골드셋·동일 pgvector**, 바꾸는 건 *임베딩 모델 하나*뿐.
2. 각 모델로 코퍼스 적재(passage 모드) → 골드 쿼리 검색(query 모드) → 지표 산출.
3. 표본 규모(초안): 법안 **50~100건** + 대응 현행법, 시나리오 A 정답쌍 수백, 시나리오 B 질의 30~50.
4. 동일 top-k, 동일 거리(코사인), 동일 청크 정책.

---

## 4. 판정 룰

- **1순위: 검색 정확도** — 시나리오 A·B의 `Recall@5`·`MRR@10`. 목표선(초안) **Recall@5 ≥ 0.80**.
- **동률·근소차 시 2순위:** 단가 → 지연 → 차원(저장).
- 정확도 차가 유의미하지 않으면 **저비용·저차원(OpenAI 1536) 채택**, Upstage가 한국어에서 *뚜렷이* 앞서면 비용 감수.
- 결과는 [[decision-log]]에 벤더 확정으로 기록.

---

## 5. 데이터 수집 파이프라인 연계 (선행 작업)

벤치는 코퍼스가 있어야 돈다. 수집 파이프라인이 다음을 산출한다:
- **법안**: 열린국회·법제처 커넥터 → Normalizer → `Bill`/`Article`(+**신구조문대비표** 파싱 = 시나리오 A 정답쌍)
- **현행법**: 국가법령정보 커넥터 → 조문(시나리오 A 검색 대상)
- **법안 요약/LawFacts**: 시나리오 B 검색 대상
- 소규모면 충분 — 전수 수집 불필요.

→ 즉 **수집 파이프라인(MVP §4)을 먼저 최소 구현** → 골드셋 추출 → 벤치 실행 순서.

## 6. 산출물

- 모델별 지표 표(시나리오 A·B × Recall/MRR/nDCG + 운영지표)
- 실패 사례 모음(정성)
- **벤더·차원 확정** → component-specs §3.3 갱신 + decision-log 기록
- 재현 스크립트(동일 코퍼스/골드셋으로 재실행 가능)
